# NPU 연산 실습 과제: 배열 차원 축소와 오버헤드 탐구 노트

## 1. NPU 연산에서의 오버헤드 (Overhead) 분석

단순 ALU 연산 시간 외에, 작업을 수행하기 위해 본질적으로 수반되는 부가적인 시간(메모리 전달, 제어 신호 교환 등)이 존재합니다. 따라서 **연산 데이터의 규모가 작을 때는 오버헤드가 전체 실행 시간을 지배**하게 됩니다.

### 오버헤드가 발생하는 주요 단계

1. **CPU 명령 준비**: 드라이버 호출 및 NPU API 실행 준비 과정.
2. **BUS 통신 설정**:
   * PCIe 컨트롤러 설정.
   * CPU-NPU 칩셋 간 전기 신호 제어 및 데이터 전송 프로토콜 핸드셰이크.
3. **데이터 버스 이동**: 실제 데이터 전송 전후의 제어 신호 교환.

>  **핵심 원인**: 전송하는 데이터가 단 1바이트에 불과하더라도 위의 **기본 고정 오버헤드 비용(Fixed Overhead)**은 동일하게 발생합니다.

---

### 데이터 크기에 따른 실행 시간 비교

* **데이터량이 매우 큰 경우 (예: $1000 \times 1000$ Matrix)**
  * 기본 오버헤드: $0.01\,\text{ms}$
  * 실제 NPU 연산 시간: $1000\,\text{ms}$
  * **결과**: 전체 실행 시간 중 순수 연산 비중이 압도적으로 높아 NPU 가속 효과가 극대화됩니다.

* **데이터량이 매우 작은 경우 (예: $3 \times 3$ 또는 $13 \times 13$ Matrix)**
  * 기본 오버헤드: $0.01\,\text{ms}$
  * 실제 NPU 연산 시간: $0.0001\,\text{ms}$
  * **결과**: 순수 연산 시간보다 **기본 오버헤드 시간($0.01\,\text{ms}$)이 훨씬 더 커서**, CPU 직접 연산보다 오히려 느려지거나 배열 차원을 축소(2D $\rightarrow$ 1D)해도 속도 개선이 체감되지 않습니다.

---

## 2. 파이썬 반복문 구현 방식별 속도 및 오버헤드 분석

2차원 배열을 1차원으로 평탄화하더라도, 파이썬 루프를 어떤 구문으로 순회하느냐에 따라 CPython 내부 오버헤드가 다르게 발생합니다.

### 1) 인덱스 접근 방식 (`range` 기반)

```python
total_sum = sum(d1[i] * d2[i] for i in range(size_N))

```

* **느린 이유**:
1. **`range()` 이터레이터 및 바이트코드 실행**: 루프의 매 스텝마다 변수 `i`를 파이썬 네임스페이스에 할당하고, 파이썬 인터프리터 바이트코드(`BINARY_SUBSCR` 등)를 재해석합니다.
2. **인덱싱 및 경계 검사 오버헤드**: `d1[i]`와 `d2[i]`에 접근할 때마다 리스트 객체의 메모리 주소를 참조하고, 인덱스 `i`가 리스트 범위를 벗어나지 않는지 검사(Bound Check)를 매번 2회씩 반복합니다.
3. **캐시 효율 저하**: 객체 변수를 거쳐 리스트 메모리를 매번 우회 조회하므로 CPU L1/L2 캐시 히트율이 떨어집니다.



---

### 2) `zip()` 함수 활용 방식

```python
total_sum = sum(x * y for x, y in zip(d1, d2))

```

* **개선되는 이유**:
1. **C-Level 포인터 이동**: `zip` 객체는 C 언어 수준에서 구현된 이터레이터 포인터를 사용하므로, 매 루프마다 인덱스 경계 검사를 수행하는 대신 **포인터를 메모리 상에서 직접 1칸씩 전진**시킵니다.
2. **인덱싱 연산 생략**: `d1[i]`와 같이 주소를 재계산하는 과정 없이, 포인터가 가리키는 메모리 요소에 직접 접근합니다.


* **여전히 남아있는 파이썬 레벨 오버헤드**:
* 제너레이터 표현식(`for x, y in ...`)을 사용하는 한, 파이썬 바이트코드 루프 자체는 계속 실행됩니다.
* 매 스텝마다 `(x, y)` 언팩용 임시 튜플 객체가 생성 및 해제되는 오버헤드가 일부 존재합니다.



---

### 3) `map()` 및 `operator.mul` 활용 방식

```python
import operator

total_sum = sum(map(operator.mul, d1, d2))

```

* **동작 특성**:
* `map()`과 `operator.mul`을 결합하면 파이썬 인터프리터의 바이트코드 루프(Eval Loop)를 우회하여 C-Level 포인터 순회로 곱셈을 처리하므로 파이썬 구문 중에서는 가장 빠른 편에 속합니다.


* **속도 향상 폭이 제한적인 이유**:
* `map`과 `operator`가 C 언어로 동작하더라도, 순회 대상인 `d1`, `d2` 내부의 개별 요소들은 여전히 파이썬 객체(`PyFloatObject` 또는 `PyLongObject`)로 포장(Boxed)된 상태입니다.
* 결국 C-Level 단에서 매번 파이썬 C-API를 통해 객체의 래핑을 풀고 연산하는 비용이 발생하므로, NumPy나 C/C++ 레벨의 연속된 날것의 데이터(Unboxed Raw Data) 연산 속도에는 미치지 못합니다.
* 결론적으로 데이터 이동 및 CPython 인터프리터 자체의 **기본 제어 오버헤드**가 전체 실행 시간의 상당 부분을 차지하고 있어, 차원 축소(2D $\rightarrow$ 1D) 및 구문 최적화만으로는 획기적인 Performance 향상을 얻기 어렵습니다.
```
