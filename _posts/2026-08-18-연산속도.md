# NPU 연산 실습 과제: 배열 차원 축소와 오버헤드 탐구 노트

## 1. NPU 연산에서의 오버헤드 (Overhead) 분석

단순 연산 시간 외에 작업을 위해 본질적으로 들어가는 부가적인 시간(메모리, 제어 등)이 존재하므로, 연산 규모가 작을 때는 오버헤드가 전체 실행 시간을 지배하게 됩니다.

### 오버헤드가 발생하는 주요 단계

1. **CPU 명령 준비**: 드라이버 및 API 호출을 위한 준비 과정.
2. **BUS 통신 설정**:
* PCIe 컨트롤러 설정.
* CPU-칩셋 간 전기 신호 제어 및 데이터 프로토콜 설정.


3. **데이터 버스 이동**: 실제 데이터 전송 전후의 제어 신호 교환.

> **핵심 원인**: 데이터가 단 1바이트여도 위 세 단계의 **기본 고정 오버헤드 비용**은 동일하게 발생함.

---

### 데이터 크기에 따른 실행 시간 비교

* **데이터량이 매우 큰 경우 (예: $1000 \times 1000$)**:
* 기본 오버헤드: $0.01\,\text{ms}$
* 실제 NPU 연산 시간: $1000\,\text{ms}$
* **결과**: 전체 시간 중 연산 비중이 커서 NPU 가속 효과가 극대화됨.


* **데이터량이 매우 작은 경우 (예: $3 \times 3$ Matrix / $13 \times 13$)**:
* 기본 오버헤드: $0.01\,\text{ms}$
* 실제 NPU 연산 시간: $0.0001\,\text{ms}$
* **결과**: 연산 시간보다 기본 오버헤드 시간($0.01\,\text{ms}$)이 훨씬 더 커서, CPU 직접 연산보다 오히려 느려지거나 배열 차원을 축소(2D $\rightarrow$ 1D)해도 속도 개선이 체감되지 않음.

## 2. 파이썬 반복문 구현 방식별 속도 및 오버헤드 분석

2차원 배열을 1차원으로 평탄화하더라도, 파이썬 루프를 어떤 방식으로 순회하느냐에 따라 발생하는 내부 오버헤드가 다릅니다.

### 1) 인덱스 접근 방식 (`range` 기반)

```python
total_sum = sum(d1[i] * d2[i] for i in range(size_N))

```

* **느린 이유**:
1. **`range()` 객체의 이터레이터 생성 및 바이트코드 실행**: 매 루프마다 `i`라는 변수를 파이썬 네임스페이스에 할당하고 바이트코드를 재해석함.
2. **인덱싱 오버헤드**: `d1[i]`를 구하기 위해 리스트 객체로 이동한 뒤, 인덱스 `i`가 범위(Bound)를 벗어나지 않았는지 경계 검사(Boundary Check)를 수행함. (`d1[i]`, `d2[i]` 총 2회 검사 반복)
3. **C-Level 포인터 직접 접근 불가**: 파이썬 객체 변수를 거쳐서 리스트 메모리 주소를 매번 조회하므로 CPU 캐시 효율이 떨어짐.



---

### 2) `zip()` 함수 활용 방식

```python
total_sum = sum(x * y for x, y in zip(d1, d2))

```

* **동작 원리**: C 언어로 작성된 전용 이터레이터 Struct를 만들어 동작.
1. **인덱스 경계 검사 생략**: `zip` 객체 생성 시 두 리스트의 메모리 포인터 위치를 잡고, 루프를 돌 때 인덱스 검사 대신 **포인터를 앞으로 1칸씩 전진**시킴.
2. **인덱싱 연산 제거**: `d1[i]`처럼 주소를 다시 찾아가는 연산 없이 C 포인터가 가리키는 데이터 메모리를 바로 꺼냄.


* **여전히 존재하는 파이썬 레벨 오버헤드**:
* `for x, y in zip(...)` 제너레이터 표현식 구조는 여전히 파이썬 바이트코드 루프를 탐.
* 매 반복마다 `(x, y)` 튜플을 생성하고 해제하는 과정에서 파이썬 자체 오버헤드가 일부 유지됨.



---

### 3) `map()` 및 `operator.mul` 활용 방식

```python
map(operator.mul, d1, d2)

```

* **속도 차이가 크지 않은 이유**:
* `map`과 `operator`의 조합은 파이썬 바이트코드 인터프리터의 개입을 줄여주지만, 여전히 개별 요소들이 파이썬 객체로 포장(Boxed)된 상태에서 덧셈/곱셈이 이루어짐.
* NPU 연산처럼 데이터 이동 및 Cpython 인터프리터 자체의 **기본 제어 오버헤드**가 전체 실행 시간의 대부분을 차지하기 때문에 1차원으로 바꿨더라도 획기적인 performance 향상이 나타나지 않음.
