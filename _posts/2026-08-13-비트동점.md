# [Python] MAC 연산에서 발생한 부동소수점 비트 동점(UNDECIDED) 이슈 분석 및 해결기

NPU 및 패턴 매칭 시뮬레이터의 **MAC(Multiply-Accumulate, 곱셈-누적)** 연산 모듈을 개발하던 중, 특정 테스트 케이스에서 의외의 문제에 직면했습니다.

알고리즘 구현상으로는 문제가 없는데, 특정 패턴 입력에서 **Cross 필터 점수**와 **X 필터 점수**가 소수점 이하 하위 비트까지 100% 완벽히 일치하여 `UNDECIDED`(동점) 판정으로 테스트가 실패(FAIL)하는 현상이었습니다.

단순한 오차 문제인 줄 알고 시작했던 디버깅은 결국 **CPython의 `sum()` 내부 C-API 연산 파이프라인**과 **IEEE 754 부동소수점 연산의 근본적 특성**을 파헤치는 깊은 탐구로 이어졌습니다. 그 분석 과정을 기록으로 남깁니다.

---

## 1. 문제 상황 (Problem)

특정 테스트 케이스(`size_5_1`, `size_13_2`, `size_25_1`) 실행 시 Cross 점수와 X 점수가 정확히 동일한 값으로 출력되었습니다.

```text
-- size_5_1 ---
Cross 점수: 0.90000000000000002220446
X 점수    : 0.90000000000000002220446
판정      : UNDECIDED | expected: X | FAIL

--- size_13_2 ---
Cross 점수: 7.50000000000000000
X 점수    : 7.50000000000000000
판정      : UNDECIDED | expected: Cross | FAIL

```

반면 다른 개발자환경이나 일부 케이스에서는 아주 미세한 ULP(Unit in the Last Place) 차이가 발생하면서 정상적으로 판정이 이루어지고 있었습니다.

---

## 2. 진단 과정: 비트 단위 비교와 파이프라인 분석

### 1단계: `float.hex()`를 통한 비트 단위 검증

Python의 `float.hex()`를 사용해 IEEE 754 64비트 표현식을 추출했습니다.

```python
print(f"Cross hex: {score_cross.hex()}")
print(f"X hex    : {score_x.hex()}")
print(f"비트 동일 여부: {score_cross == score_x}")

```

```text
[진단] hex 표현 Cross: 0x1.ccccccccccccdp-1
[진단] hex 표현 X    : 0x1.ccccccccccccdp-1
비트 동일 여부: True

```

가수부 52비트 전체가 `0xccccccccccccd`로 **비트 단위 100% 일치**함을 확인했습니다.

### 2단계: 연산 구조 변경 실험 (결합법칙 미성립 확인)

부동소수점 연산은 **결합법칙이 성립하지 않습니다** $((a+b)+c \neq a+(b+c))$.
동일한 입력 데이터를 4가지 루프 구조로 다르게 누적해 보았습니다.

| 실험 방식 | 코드 구조 특징 | `size_5_1` (Cross vs X) | 결과 |
| --- | --- | --- | --- |
| **방식 1 (기존)** | Generator + `sum()` (행 우선) | `0.900...` / `0.900...` | **비트 완전 일치 (FAIL)** |
| **방식 A** | 이중 for문 (열 우선 누적) | `9.000...` / `8.999...` | 동점 해소 (스케일 차이 발생) |
| **방식 B** | 행별 부분합(`row_sum`) 후 누적 | `0.900...` / `0.899...` | 동점 해소 (미세 ULP 차이 발생) |
| **방식 C** | 이중 for문 (행 우선 명시적 누적) | `0.900...` / `0.899...` | 동점 해소 (미세 ULP 차이 발생) |

같은 행 우선 순회임에도 방식 1(`sum()`)과 방식 C(명시적 `for` 루프)의 결과가 다르게 나타났습니다.

---

## 3. 핵심 원인 분석

원인은 **입력 데이터의 공간적 대칭성**과 **CPython `sum()` C-API 연산 파이프라인**의 결합 때문이었습니다.

```python
# 기존 연산 방식
total_sum = sum(
    filter_data[r][c] * pattern_data[r][c]
    for r in range(n) for c in range(n)
)

```

1. **데이터셋의 공간적 대칭성 (Data Symmetry):**
입력 패턴과 필터(Cross, X)가 행렬 내에서 대칭 구조를 이룸에 따라, 두 연산 간 합산되는 원소들의 가중치 조합이 이론적으로 대칭을 형성합니다.
2. **CPython `sum()`의 레지스터 수렴 특성:**
CPython의 `sum()`은 C-Level 레지스터에서 고속 연속 누적을 수행합니다. 대칭 데이터셋의 중간 오차가 C-Level 누적 끝에 IEEE 754 **Round-to-Nearest-Even** 반올림 규칙에 의해 동일한 비트 오프셋으로 수렴 정리되어 버립니다.
3. **Python 버전별 `sum()` 동작 차이:**
Python 3.12부터 부동소수점 합산 시 정밀도와 교환법칙(Commutativity)을 개선하는 고정밀 알고리즘이 적용되었습니다. 이로 인해 순서가 다른 대칭 데이터셋이라도 CPython 빌드 환경에 따라 동일한 비트값으로 더 완벽하게 수렴하여 `UNDECIDED`가 발생할 확률이 더욱 높아진 것입니다.

### `sum()` vs 명시적 `for` 루프 동작 비교

| 구분 | `sum()` (제너레이터) | 명시적 `for` 루프 (`+=`) |
| --- | --- | --- |
| **연산 레벨** | CPython C-API 레벨 연속 연산 | 파이썬 인터프리터 Float 객체 레벨 |
| **오차 보존** | C-레지스터 수렴 과정에서 하위 오차 제거됨 | 매 Step마다 ULP 오프셋이 Float 객체에 보존됨 |
| **비트 일치 여부** | **`True` (수렴으로 인한 FAIL)** | **`False` (오차 보존으로 인한 PASS)** |

## 4. Step별 원소 곱셈값 및 비트 변화 추적

실제로 연산 진행 과정 중 어느 단계에서 비트가 갈라지고 수렴하는지 `size_5_1` 데이터셋으로 추적했습니다.

```python
# Step별 누적 추적 코드 요약
loop_x, loop_cross = 0.0, 0.0

for r in range(n):
    for c in range(n):
        vx = x_filter[r][c] * pattern[r][c]
        vc = cross_filter[r][c] * pattern[r][c]
        
        loop_x += vx
        loop_cross += vc
        
        # C-level sum() 연속 누적 시뮬레이션
        sum_x_sim = sum(x_terms[:step])
        sum_cross_sim = sum(cross_terms[:step])

```

### 콘솔 출력 결과 (Step 08 ~ Step 09 및 최종)

```text
Step 08 | 위치 (4,0) ==> [이번 Step 곱한값] Cross: 0.0 | X: 0.1
 ├─ [loop()] 오차 보존  | Cross: 0.9 (0x1.ccccccccccccdp-1) vs X: 0.7999999999999999 (0x1.9999999999999p-1)
 ├─ [sum() ] C-연속 누적 | Cross: 0.9 (0x1.ccccccccccccdp-1) vs X: 0.8                (0x1.999999999999ap-1)
 └─ 현재 비트 동점 여부   | loop(): False | sum(): False
------------------------------------------------------------------------------------------------------------------------
Step 09 | 위치 (4,4) ==> [이번 Step 곱한값] Cross: 0.0 | X: 0.1
 ├─ [loop()] 오차 보존  | Cross: 0.9 (0x1.ccccccccccccdp-1) vs X: 0.8999999999999999 (0x1.cccccccccccccp-1)
 ├─ [sum() ] C-연속 누적 | Cross: 0.9 (0x1.ccccccccccccdp-1) vs X: 0.9                (0x1.ccccccccccccdp-1)
 └─ 현재 비트 동점 여부   | loop(): False | sum(): True  <-- [sum() 방식만 동점 발생!]

========================================================================================================================
최종 결과 및 동점(UNDECIDED) 판정
========================================================================================================================
[sum() 방식 - C-level 파이프라인]
 ├─ Cross 점수 : 0.9                  | Hex: 0x1.ccccccccccccdp-1
 ├─ X     점수 : 0.9                  | Hex: 0x1.ccccccccccccdp-1
 └─ 판정: 반올림 규칙에 의해 완벽히 수렴함 => True (UNDECIDED / FAIL)

[loop() 방식 - 파이썬 오차 보존]
 ├─ Cross 점수 : 0.9                  | Hex: 0x1.ccccccccccccdp-1
 ├─ X     점수 : 0.8999999999999999   | Hex: 0x1.cccccccccccccp-1
 └─ 판정: 미세 오차가 끝까지 보존되어 동점 해소 => False (PASS)

```

Step 09 마지막 원소를 더하는 순간, `sum()` 파이프라인에서는 `0.8999999999999999`가 반올림 규칙에 의해 `0.9` (`0x1.ccccccccccccdp-1`)로 완전 수렴해버리지만, 명시적 `for` 루프 방식은 ULP 오차가 끝까지 보존되어 동점이 해소되는 것을 확인할 수 있습니다.

## 5. 해결 방안 및 코드 수정

핵심 MAC 연산 모듈 내 파이프라인을 `sum(generator)` 형태에서 명시적 `for` 루프 기반 순차 누적 방식으로 대체 변경하였습니다.

```python
# 수정 전 (FAIL 유발)
def calculate_mac_old(self, pattern):
    return sum(
        self.data[r][c] * pattern.data[r][c]
        for r in range(self.n) for c in range(self.n)
    )

# 수정 후 (PASS 적용)
def calculate_mac_new(self, pattern):
    total_sum = 0.0
    for r in range(self.n):
        for c in range(self.n):
            total_sum += self.data[r][c] * pattern.data[r][c]
    return total_sum

```

## 6. 결론 및 인사이트

1. **부동소수점 연산에는 '완벽한 정답'이 없다:**
컴퓨터 시스템의 부동소수점 연산에서는 "어떤 파이프라인과 순서로 더하느냐"에 따라 동일 수식도 결과 비트가 달라질 수 있습니다.
2. **CPython 추상화 내부 파이프라인의 이해:**
파이썬 내장 함수(`sum()`)는 C-Level 최적화가 들어가 있어 매우 빠르고 정밀하지만, 데이터의 공간적 대칭성과 결합하면 원치 않는 **비트 수렴 현상**을 유발할 수 있습니다.
3. **디버깅 도구로서의 `float.hex()`:**
10진수 출력 형태로는 잘 보이지 않는 미세 오차나 완전 동점 여부를 판별할 때, 16진수 비트 표현식(`hex()`)이 가장 확실한 디버깅 도구가 되어줍니다.
